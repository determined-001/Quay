# Anchor due diligence

This describes the implemented `OFFRAMP=anchor` / `testanchor` seller-initiated flow. The production adapter uses SEP-10, SEP-12, SEP-38 and SEP-6; the SEP-24 adapter exists in source but is not wired into the API. An anchor must confirm its own licensing, supported corridor, KYC fields, payout rail, data retention, and incident contact before launch. [API wiring: `createAnchor`, `createOffRamp`](../apps/api/src/services/container.ts) · [Mainnet anchor requirements](MAINNET.md#phase-1--choose-an-anchor) · [SEP-24 limitation](ARCHITECTURE.md#4-cash-out--sep-24-interactive-variant-per-anchor-selection-tracked-in-216-quote-gaps-in-217219)

## Custody and authority

```text
Buyer wallet ── Stellar payment ──> Seller wallet
                                  │
                                  └── seller-signed withdrawal transfer ──> Anchor wallet ──> payout rail
Quay API (production, DEFAULT_SELLER_SECRET unset): link tracking, KYC relay, quotes, withdrawal initiation, status
```

`POST /links` sets the payment destination to the authenticated seller's wallet, and the browser asks the seller's wallet to sign any later withdrawal transfer. Quay's current service composition gives the anchor adapter a seller-scoped JWT, not a seller keypair; the server cannot sign a payment or a seller's SEP-10 challenge with its production signing key. The planned inline mode is not implemented. [Link destination: `LinkService.createLink`](../apps/api/src/services/link-service.ts) · [Wallet transfer signing: `signTransaction`, `sendAnchorTransfer`](../apps/web/lib/wallet.ts) · [Anchor wiring: `createAnchor`](../apps/api/src/services/container.ts) · [Modes: `OffRampMode`](../packages/core/src/ports/index.ts)

The seller's anchor JWT is a **bearer credential**, even though it cannot sign a Stellar payment. It can read or update that seller's KYC and initiate a withdrawal request; treat theft of it as a privacy and payout incident. The anchor pays only after the seller separately signs and sends the requested asset. ## Data flow and retention

Production integration must use HTTPS end to end. The public-network configuration rejects a non-HTTPS `ANCHOR_URL`, and SEP-1 discovery itself uses HTTPS. The client ignores any endpoint advertised in the anchor's TOML that is not an `https:` URL (it keeps the guessed `https://<home domain>/…` path instead), but it applies no host or address check to an HTTPS endpoint, so verify **each** advertised SEP endpoint points at the anchor's own infrastructure before launch. SEP-6 withdrawal initiation uses a GET whose query string carries the payout values the anchor's chosen withdrawal type declares (for example `dest` and `dest_extra`), so the anchor must keep URL/access logs appropriately protected. Stellar payments and seller withdrawal transfers are submitted to the public ledger. The table describes Quay's local persistence. **Retention is partial.** Three jobs delete data: a daily KYC and identity retention sweep (`runKycRetentionSweep`), which runs when `KYC_RETENTION_DAYS` is greater than 0 (default 730; 0 disables it) and, for sellers inactive for longer than that, erases `seller_profile`, `kyc_disclosure_fields`, `seller_kyc`, `kyc_consents` and `anchor_sessions` rows and clears the saved payout fields, skipping any seller with a link in `offramp_pending`; an hourly sweep of `anchor_sessions` rows that expired more than a grace period ago (`ANCHOR_SESSION_SWEEP_GRACE_MS`); and an hourly sweep of expired `revoked_tokens` rows. A seller can also erase their identity data on request (`DELETE /seller/profile`, which asks the anchor to erase first and then runs the same local erasure, `eraseSellerIdentityLocal`). **There is no deletion job for the `sellers` row itself, `links`, `link_payments`, off-ramp quotes, jobs or telemetry, or webhook rows and delivery history; the retention sweep deliberately keeps them.** Expiry on a link, quote, JWT, or webhook secret changes validity/state; it is not a data-deletion promise. Anchor-side retention, backup retention, and legal retention must be agreed with the operator and anchor separately. ## Seller identity and wallet changes

Each seller is their **own anchor customer**: the expected JWT `sub` is the seller's wallet. Quay rejects a token whose `sub` is missing, is not exactly the seller's account (including `G...:memo` and `M...` forms), or whose `iss`, `exp`, `iat` or `home_domain` claims fail the checks above (issue 3.11). The signature is not verified because SEP-10 does not publish the anchor's JWT key. Quay only reuses an anchor session when its stored account matches the current seller account. A changed wallet needs a new wallet-signed anchor challenge; signing in with another wallet ordinarily creates a distinct seller record. The KYC adapter does not reuse an anchor `customer_id` from another account. ## Contacts and incidents

Before integration, exchange named security and operations contacts with the anchor, agree an incident notification channel and response window, and document who can suspend withdrawals, revoke anchor JWTs, rotate encryption keys and notify affected sellers. Quay's operational response steps are in the [runbook](RUNBOOK.md#anchor-incidents) and its [incident template](RUNBOOK.md#incident-template); report vulnerabilities privately through [SECURITY.md](../SECURITY.md#reporting-a-vulnerability). These are integration actions for the operator, not promises that an anchor contract or notification SLA already exists. [Mainnet agreement requirement](MAINNET.md#phase-1--choose-an-anchor)
