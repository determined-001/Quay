# Threat model: seller-signed anchor authentication and withdrawals

Scope: the current seller-initiated SEP-10 → SEP-12 → SEP-38 → SEP-6 flow. The [architecture cash-out sequence](ARCHITECTURE.md#3-cash-out--sep-10--sep-38--sep-6-testanchorofframp-todays-real-adapter) is the happy path; the SEP-24 adapter (`AnchorOffRamp`) is not wired into the API. This is a code-level model, not an assurance about an anchor's operations or the safety of a seller's wallet. Evidence links name the symbol to look for rather than a line range, so they do not drift. [Active adapter wiring: `createAnchor`, `createOffRamp`](../apps/api/src/services/container.ts) · [Stellar SEP-10](https://github.com/stellar/stellar-protocol/blob/master/ecosystem/sep-0010.md) · [Stellar SEP-6](https://github.com/stellar/stellar-protocol/blob/master/ecosystem/sep-0006.md)

## Assets and authority

| Asset | Owner / consequence if lost | Current boundary |
| --- | --- | --- |
| Seller USDC and wallet signing authority | Seller owns funds. A malicious payment signature can transfer them. | The browser asks the seller's wallet to sign the anchor challenge and later the withdrawal transfer. The active API adapter never holds a seller signing key: the public network refuses to boot with `DEFAULT_SELLER_SECRET` set, and on testnet the server only reads the matching public key from it. [Wallet: `signChallenge`, `signTransaction`, `sendAnchorTransfer`](../apps/web/lib/wallet.ts) · [Wiring: `createAnchor`, `createOffRamp`](../apps/api/src/services/container.ts) |
| Anchor SEP-10 JWT | Bearer authority to read/update the seller's SEP-12 record and request an SEP-6 withdrawal; stolen JWT can expose or change identity data and start a withdrawal, but cannot itself sign the on-chain funding transfer. | `anchor_sessions.token_encrypted` uses `WEBHOOK_SECRET_ENCRYPTION_KEY`; Quay decrypts it to call the anchor. [Port: `AnchorSession`, `AnchorSessionRepository`](../packages/core/src/ports/index.ts) · [Repository: `DrizzleAnchorSessionRepository`](../apps/api/src/repos/index.ts) · [Adapter: `TestAnchorOffRamp.initiate`](../packages/offramp/src/testanchor.ts) |
| SEP-12 identity fields | Seller PII; disclosure or cross-seller overwrite harms privacy and KYC integrity. | Two stores hold the values, both under `KYC_ENCRYPTION_KEY`: `seller_kyc.fields_encrypted` (the submission to one anchor) and `seller_profile.value_encrypted` (the reusable profile, one encrypted row per SEP-9 field). Account, customer ID, status, field requirements, per-field status, sent field names and message are stored separately without field encryption. [Schema: `sellerKyc`, `sellerProfile`](../apps/api/src/db/schema.ts) · [Repositories: `DrizzleKycRepository`, `DrizzleSellerProfileRepository`](../apps/api/src/repos/index.ts) |
| Saved payout fields | Bank destination and related details; disclosure can expose financial information. | `sellers.payout_fields_encrypted` holds them as an AES-256-GCM blob under `KYC_ENCRYPTION_KEY`; the dashboard also masks them. `savePayoutFields` writes nothing when no key is configured, and real anchors require the key at boot. `sellers.payout_fields_json` is a deprecated legacy column: `rowToSeller` still reads it as a fallback, and `backfillLegacyPayoutFields` re-encrypts and nulls it at boot once a key is set, so a plaintext value can only survive on a database that has never booted with the key. [Schema: `sellers`](../apps/api/src/db/schema.ts) · [Write: `rowToSeller`, `savePayoutFields`, `backfillLegacyPayoutFields`](../apps/api/src/repos/index.ts) |
| `KYC_ENCRYPTION_KEY` | Decrypts the stored SEP-12 field values and payout fields if an attacker also has a database copy. | Parsed as a 32-byte key (with an optional key ring of previous keys, `KYC_ENCRYPTION_KEY_PREVIOUS`, for rotation); AES-256-GCM protects each stored blob. [Key parsing and encryption: `parsePiiKey`, `parsePiiKeyring`](../apps/api/src/crypto/pii.ts) · [Repositories](../apps/api/src/repos/index.ts) |
| `SERVER_SIGNING_SECRET` | Quay's own SEP-10 login identity. Theft lets an attacker sign a challenge as Quay if they can present it to wallets; it does not mint Quay sessions without `JWT_SECRET` and is not a seller payment key. | Used by `ChallengeService` to sign Quay's own login challenges. Only when `ANCHOR_CLIENT_DOMAIN=true` is it also used to co-sign the anchor's SEP-10 `client_domain` operation (`createClientDomainSigner`), which moves no funds. [Container: `ChallengeService` construction](../apps/api/src/services/container.ts) · [Challenge: `ChallengeService`](../apps/api/src/services/challenge.ts) · [Client-domain signer](../apps/api/src/services/client-domain-signer.ts) |
| `JWT_SECRET` | Signs Quay seller sessions; theft permits forged Quay API authentication until rotation. | It is separate from seller wallet signatures and anchor-issued JWTs. [Session issuer: `SessionIssuer`](../apps/api/src/services/session.ts) · [Container: `resolveJwtSecret`](../apps/api/src/services/container.ts) |
| `WEBHOOK_SECRET_ENCRYPTION_KEY` | Decrypts stored anchor JWTs as well as webhook signing secrets. Theft together with DB access widens the incident from metadata to bearer credentials. | Required at production boot; AES-256-GCM protects the stored values. [Key loading and encryption: `resolveKey`, `assertKeyConfigured`, `encryptSecret`, `decryptSecret`](../apps/api/src/services/secret-crypto.ts) |

## Actors and trust boundaries

1. **Seller and wallet → browser.** Quay's UI can prepare XDR, but only the selected wallet can authorize a signature. A compromised browser or malicious wallet extension can alter what is presented for signing; the wallet confirmation remains a separate trust boundary. [Wallet signing: `signChallenge`, `signTransaction`](../apps/web/lib/wallet.ts)
2. **Browser / API-key integrator → Quay API.** Seller sessions or scoped API keys authenticate requests; `offramp:initiate` gates anchor auth and cash-out. A stolen scoped API key is meaningful authority even without the wallet key. The cash-out route checks link ownership. [Auth middleware: `buildAuthMiddleware`, `requireScope`](../apps/api/src/middleware/auth.ts) · [Anchor route: `anchorAuthRoutes`](../apps/api/src/routes/anchor-auth.ts) · [Cash-out route: `POST /:id/cash-out`](../apps/api/src/routes/links.ts)
3. **Quay API ↔ Quay DB.** The API decrypts anchor JWTs, KYC fields, profile values and payout fields in process. DB-only access exposes other plaintext seller and transaction metadata; key compromise exposes protected values too. [Repositories](../apps/api/src/repos/index.ts) · [Schema](../apps/api/src/db/schema.ts)
4. **Quay API ↔ anchor.** The anchor controls SEP-1 discovery, SEP-10 challenge/JWT issuance, KYC responses, quotes, withdrawal destination and memo. Quay verifies the challenge but must still trust the anchor's operational integrity and the deposit instructions it returns. [Discovery and verification: `SellerAnchorAuth.challenge`, `verifiableDiscovery`, `verify`](../packages/offramp/src/anchor-session.ts) · [Withdrawal response: `TestAnchorOffRamp.initiate`, `status`](../packages/offramp/src/testanchor.ts)
5. **Browser / Quay API ↔ Horizon.** Horizon supplies account and payment state; the browser submits a seller-signed withdrawal transaction there. A wrong network, destination or memo can leave funds at the wrong place or uncredited by the anchor. [Wallet transfer: `sendAnchorTransfer`, `findAnchorTransfer`](../apps/web/lib/wallet.ts) · [Network discovery: `fetchStellarToml`, `parseStellarToml`](../packages/offramp/src/sep1.ts)

## Threats, controls and remaining exposure

The categories are a compact STRIDE-style checklist. “Control” means implemented in the linked code; a link to a follow-up issue means the gap is still open.

| Threat | Current control and evidence | Remaining exposure |
| --- | --- | --- |
| **Tampering: a malicious or compromised anchor serves a payment disguised as a SEP-10 challenge.** | Before sending XDR to the wallet, `SellerAnchorAuth` requires discovered `SIGNING_KEY` and calls `WebAuth.readChallengeTx` with the expected network, home domain and endpoint host. It re-verifies the signed XDR before relaying it. Failed discovery or missing signing key is rejected. [Challenge: `SellerAnchorAuth.challenge`](../packages/offramp/src/anchor-session.ts) · [Verification: `verifiableDiscovery`, `verify`](../packages/offramp/src/anchor-session.ts) · [Test: “refuses a challenge not signed by the anchor's published SIGNING_KEY”](../packages/offramp/test/anchor-session.test.ts) | A compromised trusted anchor can still give harmful *withdrawal deposit instructions* after authentication. The seller must review the wallet's payment prompt. [Transfer: `sendAnchorTransfer`](../apps/web/lib/wallet.ts) |
| **Spoofing: challenge is for another account, or JWT is issued to another seller.** | The decoded challenge account must equal the authenticated seller wallet. A JWT whose `sub` is missing or is not exactly the seller's account is rejected, as are bad `iss`, `exp`, `iat` and `home_domain` claims (far-future `exp` is capped at 7 days); sessions are keyed by seller and anchor. [Checks: `SellerAnchorAuth.checkClaims`](../packages/offramp/src/anchor-session.ts) · [Challenge account: `SellerAnchorAuth.verify`](../packages/offramp/src/anchor-session.ts) · [Tests: the “JWT claims are checked before a session is stored” block and “refuses a signed challenge for a different account than the signed-in seller”](../packages/offramp/test/anchor-session.test.ts) | The JWT signature is not verified locally (SEP-10 publishes no JWT key), so the claims are a sanity check, not proof of origin. |
| **Elevation of privilege: one seller reads or overwrites another seller's KYC or withdraws their link.** | Anchor auth uses the seller's wallet, KYC only reuses a `customer_id` for the same account, and cash-out checks link ownership. API keys need `offramp:initiate` for KYC, anchor auth and cash-out. [KYC account check: `TestAnchorKyc.status`, `reusableCustomerId`](../packages/offramp/src/kyc.ts) · [KYC scope: router-level `requireScope("offramp:initiate")`](../apps/api/src/routes/kyc.ts) · [Route ownership: `POST /:id/cash-out`](../apps/api/src/routes/links.ts) · [Cross-seller tests: “keeps a separate session per seller, each for that seller's own account” and “submits each seller's identity under their own account, never overwriting another's”](../packages/offramp/test/anchor-session.test.ts) | Theft of a seller session or sufficiently scoped API key permits actions in that seller's scope. Protect and revoke those credentials. [Auth scopes: `requireScope`](../apps/api/src/middleware/auth.ts) |
| **Information disclosure: Quay DB is copied.** | Anchor JWTs (`WEBHOOK_SECRET_ENCRYPTION_KEY`) and submitted KYC, profile and payout values (`KYC_ENCRYPTION_KEY`) use separate AES-256-GCM keys; raw values are decrypted in the API process. Expired anchor-session rows are swept hourly (`anchorSessionsRepo.sweepExpired` with `ANCHOR_SESSION_SWEEP_GRACE_MS`). [Token encryption: `DrizzleAnchorSessionRepository`](../apps/api/src/repos/index.ts) · [PII encryption: `DrizzleKycRepository`, `DrizzleSellerProfileRepository`, `savePayoutFields`](../apps/api/src/repos/index.ts) · [Sweep timer: `createContainer`](../apps/api/src/services/container.ts) | Wallet/account IDs and KYC metadata are plaintext. If the attacker also obtains either encryption key, the values it protects are exposed. A database that has never booted with `KYC_ENCRYPTION_KEY` may still hold a legacy plaintext `payout_fields_json` value until the boot backfill runs. [Schema](../apps/api/src/db/schema.ts) |
| **Repudiation: sensitive KYC reads cannot be tied to a specific operator action.** | The API uses structured logs with request context and redacts common PII/secret-shaped fields. [Logger: `REDACT_PATHS`](../apps/api/src/logger.ts) · [Request context: `requestContext`](../apps/api/src/request-context.ts) | There is no dedicated audit event for each PII decrypt, so a DB/key or server compromise may be hard to reconstruct. [Repository decrypt: `DrizzleKycRepository.rowToRecord`](../apps/api/src/repos/index.ts) · [#280: PII access audit](https://github.com/determined-001/Quay/issues/280) |
| **Elevation of privilege: Quay server or secret store is compromised.** | In the active SEP-6 path the server holds the seller JWT, not the seller wallet key; it cannot sign a seller transfer or anchor challenge. `SERVER_SIGNING_SECRET` signs Quay login challenges. On the public network the API refuses to boot with `DEFAULT_SELLER_SECRET` set (the guard block in `env.ts`), and the SEP-24 adapter (`AnchorOffRamp`) holds no signing key; `scripts/check-no-server-signing.mjs` fails CI if a server-held signing path returns. [Composition: `ChallengeService` and `SessionIssuer` construction](../apps/api/src/services/container.ts) · [Anchor wiring: `createAnchor`](../apps/api/src/services/container.ts) · [Boot guard](../apps/api/src/env.ts) · [Guard script](../scripts/check-no-server-signing.mjs) | A server compromise can read decrypted tokens/PII and initiate withdrawals. On testnet `DEFAULT_SELLER_SECRET` can still be configured and loaded, but the server only reads the matching public key from it. [Resolver: `resolveSellerKeypairOrWallet`](../apps/api/src/services/seller-wallet.ts) |
| **Tampering / loss: wrong asset, destination or memo on the withdrawal payment.** | The SEP-6 adapter returns the asset/amount it quoted and the anchor's destination and memo; the browser builds the transaction with those instructions and asks the seller wallet to sign. It does not invent a memo type. [Adapter: `TestAnchorOffRamp.status`](../packages/offramp/src/testanchor.ts) · [Wallet: `sendAnchorTransfer`](../apps/web/lib/wallet.ts) · [Test: “withdraws as the seller and returns the transfer for their wallet to sign”](../packages/offramp/test/anchor-session.test.ts) | The destination/memo are supplied by the anchor; no independent allowlist or out-of-band confirmation exists. A wrong or late memo can strand funds at the anchor. [Wallet warning: `sendAnchorTransfer`](../apps/web/lib/wallet.ts) |
| **Denial of service: anchor JWT expires during an in-flight withdrawal.** | `SellerAnchorAuth.token()` refuses absent, changed-wallet or near-expiry sessions with a 60-second skew; a new cash-out fails with `anchor_auth_required` rather than silently using another seller's JWT. When the pending-job poller hits the same condition it does not treat it as an anchor outage: `blockOnAnchorAuth` records the typed reason `anchor_auth_required` on the job (no backoff, link not failed), and `POST /seller/anchor-auth` calls `clearAnchorAuthBlock` so the next tick after the seller re-authenticates polls it immediately. [Session check: `SellerAnchorAuth.token`, `live`](../packages/offramp/src/anchor-session.ts) · [API mapping: `anchorAuthRequired`](../apps/api/src/services/link-service.ts) · [Poller: `LinkService.pollCashOuts`, `blockOnAnchorAuth`, `clearAnchorAuthBlock`](../apps/api/src/services/link-service.ts) | A funded withdrawal that is pending while the seller's session lapses makes no progress until the seller reconnects their wallet to the anchor; the withdrawal stays alive at the anchor in the meantime. |
| **Spoofing / stale authorization: seller logs out or changes wallet.** | A stored anchor session is only used if its account matches the current seller wallet (a different wallet is a different seller). `POST /auth/logout` deletes all of the seller's stored anchor sessions (best effort: a failure is logged and the logout still completes), and the anchor-auth disconnect route deletes its row. [Account check: `SellerAnchorAuth.live`](../packages/offramp/src/anchor-session.ts) · [Logout: `onLogout` wiring](../apps/api/src/index.ts) · [Delete: `DrizzleAnchorSessionRepository.deleteAllForSeller`](../apps/api/src/repos/index.ts) · [Disconnect: `DELETE /`](../apps/api/src/routes/anchor-auth.ts) · [Test: “treats a session for the seller's previous wallet as no session”](../packages/offramp/test/anchor-session.test.ts) | Quay deletes its stored copy but cannot revoke the JWT at the anchor (SEP-10 defines no revocation), so a token that was exfiltrated earlier stays valid there until its `exp` (capped at 7 days). A session that simply expires without a logout is removed by the hourly sweep rather than at once. |
| **SSRF / disclosure: anchor advertises an unexpected endpoint.** | SEP-1 discovery itself uses HTTPS, public-network `ANCHOR_URL` must begin with HTTPS, network mismatch is rejected, auth refuses guessed discovery or a missing signing key, and `parseStellarToml` ignores any advertised SEP endpoint that is not a parsable `https:` URL. [SEP-1: `fetchStellarToml`, `parseStellarToml`](../packages/offramp/src/sep1.ts) · [URL guard: the `ANCHOR_URL` https check](../apps/api/src/env.ts) · [Auth guard: `verifiableDiscovery`](../packages/offramp/src/anchor-session.ts) | The advertised SEP endpoint URLs are used without a per-endpoint host or private-address check (the scheme check is the only one). Verify an anchor's TOML and endpoint allowlist before production; do not equate the webhook SSRF guard with anchor URL protection. [Endpoint use: `SellerAnchorAuth.challenge`](../packages/offramp/src/anchor-session.ts) · [#286: mainnet TOML preflight](https://github.com/determined-001/Quay/issues/286) |
| **Denial of service: challenge-route abuse.** | A global IP limiter covers the API, and `/auth` has an additional strict limiter. Anchor auth requires a seller session or API key with `offramp:initiate`, and `anchorAuthLimit` (keyed `anchor-auth:<seller id>`) is applied to both `POST /seller/anchor-auth/challenge` and `POST /seller/anchor-auth`, so one credential cannot amplify traffic at the anchor from many IPs. [Global/strict wiring: the `rateLimit` setup, `strictRateLimit`, `anchorAuthLimit`](../apps/api/src/index.ts) · [Anchor auth: `anchorAuthRoutes`](../apps/api/src/routes/anchor-auth.ts) | None specific to this route beyond the shared limiter budget: an authorized client can still spend its per-seller budget on anchor requests. |

## Unhappy paths

```mermaid
sequenceDiagram
  participant Seller as Seller and wallet
  participant UI as CashOutModal
  participant API as Quay API
  participant Auth as SellerAnchorAuth
  participant Anchor as Anchor
  participant Horizon

  Seller->>API: Request anchor challenge
  API->>Auth: challenge(seller account)
  Auth->>Anchor: GET SEP-10 challenge
  alt Invalid signing key, network, domain or account
    Auth-->>API: AnchorChallengeError
    API-->>Seller: 502 challenge_rejected; no wallet prompt
  else Verified challenge
    API-->>Seller: Verified XDR
    Seller->>Seller: Wallet signs challenge
    Seller->>API: POST signed XDR
    alt Signed challenge for another account
      API-->>Seller: 400 challenge_rejected
    else Signed challenge valid
      Auth->>Anchor: POST signed XDR
      Anchor-->>Auth: Seller JWT
      alt JWT subject names another account
        Auth-->>API: AnchorChallengeError
        API-->>Seller: 400 challenge_rejected
      else Token accepted
        Auth-->>API: Encrypted session saved
      end
    end
  end

  Seller->>UI: Start cash-out
  UI->>API: POST cash-out
  alt No live seller anchor session
    API-->>UI: 403 anchor_auth_required
    UI-->>Seller: Reconnect wallet to anchor
  else Live session
    API->>Anchor: SEP-6 withdraw with seller JWT
    alt Deposit instructions not yet returned
      Anchor-->>API: Withdrawal id only
      API-->>UI: Pending job without transfer
      Note over UI,Anchor: pollCashOuts picks the instructions up at pending_user_transfer_start, fires offramp.transfer_required once, and GET /links/:id/cash-out/transfer serves them
    else Deposit instructions returned
      Anchor-->>API: Destination, asset, amount, memo
      API-->>UI: Transfer instructions
      alt Seller closes modal before sending
        Note over Seller,UI: The link page offers "Send USDC to finish cash-out", which re-reads the instructions from the API
      else Seller confirms wallet payment
        UI->>Seller: Request payment signature
        Seller->>Horizon: Submit signed withdrawal transfer
      end
    end
  end
```

Challenge and JWT failures follow the [anchor-auth route](../apps/api/src/routes/anchor-auth.ts) (`anchorAuthRoutes`, where `CHALLENGE_MESSAGES` holds the fixed seller-facing text per failure kind). Missing sessions map to HTTP 403 `anchor_auth_required` ([`anchorAuthRequired`](../apps/api/src/services/link-service.ts)). When the SEP-6 adapter returns only a pending job because no deposit account is provided yet, [`TestAnchorOffRamp.status`](../packages/offramp/src/testanchor.ts) returns the `transfer` once the anchor reaches `pending_user_transfer_start`; [`LinkService.pollCashOuts`](../apps/api/src/services/link-service.ts) fires `offramp.transfer_required` once (guarded by `transferNotifiedAt`) and logs `cashout.transfer_required`, and the seller fetches the instructions with `GET /links/:id/cash-out/transfer` ([links routes](../apps/api/src/routes/links.ts)). If the modal closes before the seller sends, the link page offers `PendingTransferAction` ([`TimelineClient.tsx`](../apps/web/app/links/%5Bid%5D/TimelineClient.tsx)) while `offrampStatus === "awaiting_transfer"`; it re-reads the instructions from the API, and [`TransferStep.tsx`](../apps/web/app/components/TransferStep.tsx) keeps a per-link sent-hash guard in `sessionStorage` so a reload cannot double-send. The modal's own transfer step and its resume path are in [`CashOutModal.tsx`](../apps/web/app/components/CashOutModal.tsx). These gaps were tracked in #206 and #250 and are closed.

## Review triggers and open work

Revisit this model whenever an adapter, JWT validator, anchor URL parser, session lifecycle, wallet signing path or API-key scope changes. The dormant server-signing paths (#207) were deleted and `scripts/check-no-server-signing.mjs` now fails CI if one returns, so they are no longer tracked here; the JWT claim checks (#208), expired-session handling in the poller (#227), logout revocation (#230), the expired-row sweep (#231), the per-seller challenge limit (#232) and the public-network seller-key refusal (#278) have likewise shipped. The open items are [#280 PII access audit](https://github.com/determined-001/Quay/issues/280) and [#286 mainnet TOML preflight](https://github.com/determined-001/Quay/issues/286). The wallet signature and anchor's operational controls remain trust assumptions even after these items land.
